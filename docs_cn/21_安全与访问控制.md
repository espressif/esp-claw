# 21 安全与访问控制

## 概述

esp-claw 的访问控制体系以 **调用者身份（Caller）**、**能力标志（Flags）** 和 **请求门控（Request Gate）** 三层机制构成，并通过 `session_id` 提供会话隔离。本文档描述各层的完整语义和实现位置。

---

## 1. CLAW_CAP_CALLER_* 枚举

定义于 `claw_modules/claw_cap/include/claw_cap.h`：

```c
typedef enum {
    CLAW_CAP_CALLER_SYSTEM  = 0,
    CLAW_CAP_CALLER_AGENT   = 1,
    CLAW_CAP_CALLER_CONSOLE = 2,
} claw_cap_caller_t;
```

| 枚举值 | 数值 | 调用来源 | LLM 可见性检查 |
|--------|------|---------|--------------|
| `CLAW_CAP_CALLER_SYSTEM` | 0 | 系统内部调用（事件路由器、Lua 脚本、其他 C 代码）| **跳过**（可调用任意能力）|
| `CLAW_CAP_CALLER_AGENT` | 1 | LLM 的工具调用（通过 `claw_core_call_cap_fn`）| **执行**（受 LLM 可见性过滤）|
| `CLAW_CAP_CALLER_CONSOLE` | 2 | 控制台命令行调用 | **跳过**（保留，当前等同 SYSTEM）|

### 调用者身份的设置时机

- **AGENT**：在 `claw_cap_call_from_core()` 中自动设置：
  ```c
  ctx.caller = CLAW_CAP_CALLER_AGENT;  // 来自 LLM 工具调用
  ```
  以及 `claw_cap_tools_collect()` 中构建工具列表时。

- **SYSTEM**：在事件路由器直接调用能力时（`claw_cap_call()`）、Lua 的 `capability.call()` 中：
  ```c
  ctx->caller = CLAW_CAP_CALLER_SYSTEM;  // lua_module_capability.c
  ```

## 2. 能力标志（Flags）

定义于 `claw_cap.h`：

```c
typedef enum {
    CLAW_CAP_FLAG_CALLABLE_BY_LLM      = 1 << 0,  // 允许 LLM 工具调用
    CLAW_CAP_FLAG_EMITS_EVENTS         = 1 << 1,  // 产生事件
    CLAW_CAP_FLAG_SUPPORTS_LIFECYCLE   = 1 << 2,  // 实现 init/start/stop
    CLAW_CAP_FLAG_RESTRICTED           = 1 << 3,  // 内部/管理专用，不暴露给 LLM
} claw_cap_flags_t;
```

### LLM 工具可见性完整条件（`claw_cap_is_llm_visible()`）

一个能力必须满足**全部**以下条件才会出现在 LLM 的工具列表中：

```c
// claw_cap.c
static bool claw_cap_is_llm_visible(const claw_cap_descriptor_slot_t *slot,
                                    const char *session_id) {
    // 1. 能力必须处于 REGISTERED 或 STARTED 状态
    if (!claw_cap_descriptor_is_available(slot)) return false;
    // 2. 必须有 execute 函数
    if (!slot->descriptor.execute) return false;
    // 3. 必须是 CALLABLE 或 HYBRID 类型
    if (kind != CLAW_CAP_KIND_CALLABLE && kind != CLAW_CAP_KIND_HYBRID) return false;
    // 4. 必须设置 CLAW_CAP_FLAG_CALLABLE_BY_LLM
    if (!(cap_flags & CLAW_CAP_FLAG_CALLABLE_BY_LLM)) return false;
    // 5. 所属 group 必须在 LLM 可见组列表中
    if (!claw_cap_group_is_llm_visible_locked(group_index, session_id)) return false;
    return true;
}
```

**因此 `CLAW_CAP_FLAG_RESTRICTED` 的能力只是不设置 `CLAW_CAP_FLAG_CALLABLE_BY_LLM`**，不受 AGENT caller 限制——但只要 caller 是 AGENT，即会被 `claw_cap_is_llm_visible` 过滤掉：

```c
// claw_cap_call() 中
if (ctx && ctx->caller == CLAW_CAP_CALLER_AGENT &&
        !claw_cap_is_llm_visible(slot, session_id)) {
    snprintf(output, output_size,
             "Error: cap '%s' is not exposed to the LLM.", ...);
    return ESP_ERR_INVALID_STATE;
}
```

### LLM 可见组管理

系统支持两级可见性配置：

| 接口 | 作用 | 位置 |
|------|------|------|
| `claw_cap_set_llm_visible_groups(groups, count)` | 设置全局 LLM 可见 group 列表 | `claw_cap.h` |
| `claw_cap_set_session_llm_visible_groups(session_id, groups, count)` | 为特定 session 设置可见 group 列表 | `claw_cap.h` |

当全局列表为空且无 session 级别配置时，**所有 group 对 LLM 可见**（默认开放）。

## 3. request_gate 的完整使用模式

`request_gate` 是 `claw_core_config_t` 中的一个函数指针，在每个请求**真正进入 Agent 循环之前**被调用：

```c
// claw_core.h
typedef esp_err_t (*claw_core_request_gate_fn)(const claw_core_request_t *request,
                                               char *reject_message,
                                               size_t reject_message_size,
                                               void *user_ctx);
```

在 `claw_core.c` 的 Agent 循环中：

```c
if (s_core->request_gate) {
    char reject_message[192] = {0};
    esp_err_t gate_err = s_core->request_gate(&request.view,
                                              reject_message,
                                              sizeof(reject_message),
                                              s_core->request_gate_user_ctx);
    if (gate_err != ESP_OK) {
        if (reject_message[0]) {
            // 将 reject_message 作为正常响应返回给用户
            response.view.status = CLAW_CORE_RESPONSE_STATUS_OK;
            response.view.text = dup_string(reject_message);
        } else {
            // 无消息时返回错误响应
            response.view.error_message = dup_string(esp_err_to_name(gate_err));
        }
        goto finish_request;  // 跳过 LLM 调用
    }
}
```

### 行为说明

- 返回 `ESP_OK`：放行请求
- 返回非 `ESP_OK` + `reject_message` 非空：将 `reject_message` 作为对话回复发送给用户，请求不传入 LLM
- 返回非 `ESP_OK` + `reject_message` 为空：产生错误响应

### 内置 request_gate 实现

记忆模块（`claw_memory`）提供 `claw_memory_request_gate_callback`，用于检测会话历史是否超出大小限制：

```c
// 当 session 被 blocked（超出 SESSION_SIZE_LIMIT）时
strlcpy(reject_message, CLAW_MEMORY_SESSION_SIZE_WARNING, reject_message_size);
return ESP_ERR_INVALID_STATE;
```

此机制防止超大会话继续向 LLM 发送请求（超出 `CLAW_MEMORY_SESSION_SIZE_LIMIT = 150 KB` 后阻断）。

## 4. session_id 的安全语义（会话隔离）

### 隔离保证

`session_id` 是 `claw_core_request_t` 中的关键字段。它决定：
1. 读取哪条历史记录（由 `persist_session` 回调实现）
2. LLM 工具列表过滤中哪些 group 可见（`session_llm_visible_groups`）
3. 记忆系统判断本次请求是否被阻塞

不同 `session_id` 的对话**完全物理隔离**，各自持有独立的历史文件。

### NOSAVE 的安全含义

会话策略 `NOSAVE` 产生空 `session_id`，导致：
- 不读取任何历史（不带上下文）
- 不写入任何历史（无法被后续请求利用）
- `request_gate` 的 session 阻塞检查跳过

这适合构建**无状态的一次性交互**，如匿名查询、测试调用。

## 5. Capability 的 DISABLED 状态与权限控制

能力组可以被动态禁用：

```c
// claw_cap.h
esp_err_t claw_cap_disable_group(const char *group_id);
esp_err_t claw_cap_enable_group(const char *group_id);
```

状态机（`claw_cap_state_t`）：

```
REGISTERED → STARTED → DISABLED
                ↑            |
                └────────────┘ (enable_group)
                     DRAINING → UNLOADING
```

DISABLED 时的行为：

| 操作 | 结果 |
|------|------|
| `claw_cap_call()` | `ESP_ERR_INVALID_STATE`（"not available"）|
| LLM 工具列表构建 | 不出现（`claw_cap_descriptor_is_available` 返回 false）|
| 注册新能力到 DISABLED 组 | 拒绝（`ESP_ERR_INVALID_STATE`）|

## 6. 能力调用的审计日志

当前通过 ESP-IDF 日志系统（`ESP_LOGI`/`ESP_LOGW`）实现审计，核心日志点：

### claw_core.c（工具调用层）

```
tool_call   request=<id> name=<cap> args=<snippet>
tool_result request=<id> name=<cap> err=<status> output=<snippet>
```

每次 LLM 工具调用的入参和出参都会被记录到日志，使用 `ESP_LOGI(TAG, ...)` 级别。

### cap_session_mgr.c（会话管理）

```
Created chat session <channel>:<chat_id> alias=<alias>
Switched chat session <channel>:<chat_id> alias=<alias>
Deleted chat session <channel> alias=<alias> history_deleted=<bool>
```

### claw_cap.c 的调用追踪

每个 `claw_cap_descriptor_slot_t` 维护 `active_calls` 计数器，记录当前正在执行的并发调用数，可通过 `claw_cap_get_descriptor_state()` 查询。

### 日志完整性说明

**目前没有独立的结构化审计日志文件**——所有调用记录依赖 ESP-IDF 串口日志。如需持久化审计，需由应用层通过 `on_request_start` 回调或自定义 `claw_cap_execute_fn` 封装来实现。

## 7. 访问控制流程图

```mermaid
flowchart TD
    A[LLM 发出 tool_call] --> B[claw_core_call_cap\ncaller=AGENT]
    B --> C{能力是否 Available？\nREGISTERED/STARTED}
    C -->|否| E1[返回 ESP_ERR_INVALID_STATE]
    C -->|是| D{caller==AGENT?\nclaw_cap_is_llm_visible?}
    D -->|不可见| E2[返回 ESP_ERR_INVALID_STATE\n"not exposed to the LLM"]
    D -->|可见| F[执行 execute 函数]
    F --> G[返回输出]

    H[系统内部调用\ncaller=SYSTEM] --> I[claw_cap_call]
    I --> C

    J[新请求入队] --> K{request_gate\n检查}
    K -->|拒绝| L[返回 reject_message]
    K -->|放行| M[进入 Agent 循环]
```

## 8. 关键安全相关常量

| 常量 | 值 | 作用 |
|------|-----|------|
| `CLAW_CAP_FLAG_CALLABLE_BY_LLM` | `1 << 0` | 允许 LLM 工具调用 |
| `CLAW_CAP_FLAG_RESTRICTED` | `1 << 3` | 标记内部能力，不暴露给 LLM |
| `CLAW_MEMORY_SESSION_SIZE_LIMIT` | 150 KB | 会话历史大小阻断阈值 |
| reject_message 缓冲区 | 192 字节 | `request_gate` 拒绝消息最大长度 |
